## Технический вопрос — закрыт

`отправить_пост_со_схемой` требует ТРИ bound'а на одном type-параметре
(`json.ИзJSON + Валидируемое + ОписаниеСхемы`). Проверено вживую (не
только чтением `parser.zig`) — `[П: Один + Два + Три]` с тремя
раздельными интерфейсами, реализованными через три ОТДЕЛЬНЫХ блока
`реализация ИмяИнтерфейса для Т` (важно: НЕ один общий `реализация Т`
— интерфейс нужно называть явно с `для`, иначе компилятор не связывает
методы с конкретным ограничением), скомпилировалось и выполнилось
корректно (`./panos file.pns` → `3`, ожидаемая сумма трёх методов).
Синтаксис объявления interface-методов БЕЗ `это` в сигнатуре (`функ
первый() -> Число`, не `функ первый(это: Один) -> Число`) — только
конкретная `реализация` добавляет `это` явно. T025 может писаться без
дополнительной проверки.

## Фактический статус (по факту реализации, не по плану выше)

**US1 (T004-T020) — ДОНЕ.** Реализация отличается от плана по форме,
не по функциональности: один файл `быстряга.pns` (не
`валидация.pns`+`приложение.pns`, см. doc-комментарий файла — panos не
поддерживает реэкспорт между модулями), `Отклик(О)` ВСЕГДА (не голое
`О`/`Отклик(О)` на выбор — см. `research.md` Вопрос про Cast_Interface
и generic-возврат), собственные `ТелоJSON`/`ОтветJSON` вместо
`json.ИзJSON`/`json.ВJSON` напрямую (коллизия имён через границу
модулей, см. doc-комментарий файла). `test_приложение.pns` — 12/12
зелёных, реальный сокет. Потребовало 5 реальных фиксов в самом
`panos` (см. `../../panos` commit "fix: пять реальных багов
VM/тайпчекера...").

**US2 (T021-T029) — ЧАСТИЧНО.** `документация()`/`swagger_ui()`
реализованы и работают (`test_документация.pns` — 10/10 зелёных):
`/openapi.json` собирается из `это.маршруты_докс` (путь+метод для
каждого маршрута, минимальный валидный `responses` без детальной
схемы), `/docs` отдаёт HTML со ссылкой на CDN Swagger UI. НЕ
реализовано: `отправить_пост_со_схемой`/`ОписаниеСхемы`/`ПолеСхемы`
(T024-T025, T028 частично) — детальная JSON Schema тела/ответа через
третий bound на type-параметре. Технический вопрос выше подтверждает,
что тройной bound `[T: A + B + C]` РАБОТАЕТ в panos, так что T025
технически осуществим — просто не сделан в этом проходе (FR-010 явно
допускает эту деградацию: путь+метод в документации есть и без схемы).

**US3 (T030-T038) — ДОНЕ.** `Далее`/`Middleware` работают на
низкоуровневом `Запрос` (не `http.ЗапросМаршрута`, см. doc-комментарий
в `быстряга.pns`) — middleware оборачивает ВЕСЬ конвейер, включая
сопоставление маршрута (`http.Маршрутизатор.обработать`), а не только
уже сматченный маршрут. `.middleware()`/`.при_старте()`/
`.при_остановке()` реализованы, `.запустить()` сворачивает
`middleware_список` справа налево вокруг `это.маршрутизатор.
обработать`. `test_middleware.pns` — 7/7 зелёных: порядок M1 -> M2 ->
обработчик (через префиксы в теле ответа — общий счётчик недоступен
между процессами), короткое замыкание (middleware не вызывает Далее —
обработчик не вызван, клиент получает ответ ОТ middleware), при_старте
вызван до первого запроса (маркер-файл).

Потребовало ЕЩЁ ОДНОГО реального фикса в panos: `eagerAliasResolutionPass`
запускался ДО `importIdentityPass` — та же identity-рассинхронизация,
что уже была найдена и исправлена для `interfacePass`/`nominalPass` (см.
основной репозиторий), только для псевдонимов ФУНКЦИОНАЛЬНОГО типа
(`тип Далее = функ(Запрос) -> http.ОтветСервера`), используемых как
