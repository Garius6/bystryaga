# Research: быстряга

## Вопрос 1 — как typed-регистрация получает СВЕЖИЙ инстанс `Тело`?

**Находка** (`std/кодирование/json.pns`, доккомент над `разобрать_в`):
в panos нет способа сконструировать `T` "из ничего" внутри
generic-кода — интерфейсные методы всегда диспетчеризуются на уже
существующем `это`, конструкторов интерфейс не даёт. Каждый
СУЩЕСТВУЮЩИЙ вызывающий код (`разобрать_в[T: ИзJSON](это: T, текст:
Строка)`) поэтому требует, чтобы вызывающий САМ создал
нулевой/дефолтный инстанс `T` заранее и передал его.

Значит generic-регистрация в `быстряга` (`получить[Тело, Ответ](путь,
обработчик)`) не может внутри себя написать `пер тело: Тело =
Тело()` — такого конструктора без аргументов у произвольной
generic-структуры нет.

**Решение**: регистрация типизированного маршрута принимает
дополнительный параметр — фабрику пустого значения:
```
быстряга.отправить_пост[Тело, Ответ](
    приложение, "/задачи",
    функ() -> Тело ЗадачаВвод("", ложь) конец,   // нулевое_тело
    функ(тело: Тело) -> Ответ ... конец            // обработчик
)
```
Многословнее FastAPI (там сигнатура функции-обработчика САМА несёт тип
параметра, рантайм-рефлексия строит инстанс автоматически) — но это
прямое следствие отсутствия рефлексии/конструкторов в panos, не
произвольный выбор дизайна. Задокументировано явно, не спрятано.

Альтернатива (отвергнута): потребовать от `Тело` отдельный интерфейс
`СНулём = интерфейс { функ нулевое() -> Тело }` — не работает по той
же причине, что и выше: `нулевое()` как СТАТИЧЕСКИЙ метод (не
привязанный к существующему `это`) panos-интерфейсы не поддерживают
(диспетчеризация всегда идёт от инстанса).

## Вопрос 2 — как быстряга читает тело запроса и как отвечает?

`ЗапросМаршрута.запрос` (`http.pns`) — обёртка над нативным opaque
`Запрос`. Подтверждено в `zig/core/type_checker.zig` (~5591-5619):
- `.тело() -> Строка` — сырое тело запроса, уже прочитанное (не
  read-once поток, можно звать один раз безопасно).
- `.метод() -> Строка`, `.путь() -> Строка`.
- `.заголовок(имя: Строка) -> Опция(Строка)`.
- `.ответить(статус: Число, тип: Строка, тело: Строка) -> Пусто` —
  НЕ используется напрямую `быстряга`-кодом (только внутри
  `Маршрутизатор.обработать`/`обслуживать_слушатель`, которые уже
  вызывают его за нас через `ОтветСервера`). `быстряга`'s обёрнутые
  обработчики просто ВОЗВРАЩАЮТ `ОтветСервера` как обычно —
  `http.Маршрутизатор` делает остальное. Значит `быстряга` не
  добавляет свой transport-слой вообще, только слой типизации ПЕРЕД
  вызовом уже существующего `ОбработчикМаршрута`.

## Вопрос 3 — где живёт валидация и как из неё вернуть 422?

`ОбработчикМаршрута = функ(ЗапросМаршрута) -> ОтветСервера` — обычная
функция, значит "обёрнутый" типизированный обработчик — это ФУНКЦИЯ
ВЫСШЕГО ПОРЯДКА: `быстряга.отправить_пост[...](...)` регистрирует в
`http.Маршрутизатор` НЕ пользовательский обработчик напрямую, а
СГЕНЕРИРОВАННУЮ обёртку вида:
```
функ(зм: ЗапросМаршрута) -> ОтветСервера
    пер тело = нулевое_тело()
    пер ошибка_разбора = json.разобрать_в(тело, зм.запрос.тело())
    если ошибка_разбора.есть() тогда
        возврат быстряга.ответ_ошибки(400.0, ошибка_разбора.получить(...).сообщение)
    конец
    пер ошибка_валид = // если Тело: Валидируемое — тело.проверить()
    если ошибка_валид.есть() тогда
        возврат быстряга.ответ_ошибки(422.0, ошибка_валид.получить(""))
    конец
    пер ответ = обработчик(тело)
    ОтветСервера(200.0, "application/json", json.сериализовать_из(ответ))
конец
```
Никакого нового транспортного механизма — чистая композиция уже
существующих `json.pns`/`http.pns` примитивов.

**Проблема**: `Валидируемое` — опциональный интерфейс (FR-004:
"если `Тело` реализует..."). panos не может проверить "реализует ли
`T` интерфейс `X`" УСЛОВНО внутри generic-функции — типовая система
здесь статическая, без `is`/`as`-подобных рантайм-проверок
реализации интерфейса произвольным generic-параметром.

**Решение** (пересмотрено после Вопроса 4): panos ДЕЙСТВИТЕЛЬНО
поддерживает конъюнкцию bound'ов — `[T: ИзJSON + Валидируемое]`
(подтверждено, см. Вопрос 4). Но конъюнкция делает `Валидируемое`
ОБЯЗАТЕЛЬНЫМ для типового параметра, не опциональным — а значит
"опциональная валидация" из исходной FR-004 не реализуема как условная
ветка внутри одной generic-функции регистрации в принципе (тип бы
либо ОБЯЗАН реализовывать интерфейс на этапе компиляции, либо нет
— рантайм-проверки "а вдруг реализует" тут нет).

Вместо двух функций регистрации (с валидацией / без) — ПРОЩЕ и
единообразнее сделать `Валидируемое` ОБЯЗАТЕЛЬНЫМ для ЛЮБОГО типа
тела типизированного маршрута (единственная сигнатура регистрации:
`[Тело: json.ИзJSON + Валидируемое]`). Структуре, которой валидация
не нужна, ничего не стоит реализовать `проверить()` тривиально
(`Опция.Нет()` всегда) — один лишний метод на структуру, не двойной
API-поверхности на весь фреймворк. Это меняет FR-004 в spec.md: было
"ЕСЛИ Тело реализует Валидируемое", стало "Тело ВСЕГДА реализует
Валидируемое" (тривиальная реализация — по-прежнему "бесплатно", раз
можно просто вернуть Нет()).

## Вопрос 4 — множественные bound'ы у одного generic-параметра?

**Подтверждено** (`zig/core/parser.zig` `parseTypeParameters`,
~строки 809-828): синтаксис `[T: ИзJSON + Валидируемое]`
поддерживается — `.plus`-токен разделяет несколько интерфейсов-bound'ов
в списке `ast.TypeParameter.bounds` (`[]const []const u8`, не
одиночная строка). Значит один type-параметр МОЖЕТ требовать
реализации сразу нескольких интерфейсов — именно это и используется
в решении Вопроса 3 выше.

**Дополнительно проверено вживую** (не только чтением кода — реальным
`./panos file.pns`, см. `tasks.md` "Технический вопрос — закрыт"): ТРИ
bound'а через `+` тоже работают (`[П: Один + Два + Три]`), при
условии, что каждый интерфейс реализован ОТДЕЛЬНЫМ блоком `реализация
ИмяИнтерфейса для Т` (не одним общим `реализация Т` без явного имени
интерфейса) — это понадобится в `plan.md` Фазе 2 для
`отправить_пост_со_схемой[Тело: json.ИзJSON + Валидируемое +
ОписаниеСхемы, ...]`.

## Вопрос 6 (найдено при реализации T005) — explicit generic args на методах

`ф[Тип](...)` (явное указание типового аргумента, `project_panos_
explicit_generic_args`) работает на СВОБОДНЫХ функциях, но НЕ на
методах — `объект.метод[Тип](...)` не парсится как generic-вызов,
парсер трактует `метод[Тип]` как ИНДЕКСАЦИЮ поля `метод` (`Type
Error: у типа нет поля 'метод'` / `индексирование поддержано только
для строки, массива и соответствия`), проверено вживую. Значит
регистрация маршрута в `быстряга` (`апи.отправить_пост(...)`) должна
ПОЛАГАТЬСЯ на инференс `Тело`/`Ответ` из типов аргументов
(`нулевое_тело: функ() -> Тело`, `обработчик: функ(Тело) -> Ответ`) —
подтверждено работающим (`к.обернуть(42.0)` на generic-методе без
explicit `[T]` выводит `T = Число` корректно). `quickstart.md`
исправлен — вызовы регистрации БЕЗ `[Тело, Ответ]` в скобках.

## Вопрос 7 (найдено при реализации T004) — нет top-level мутируемого состояния

panos допускает top-level ТОЛЬКО `конст` (примитивные литералы —
Число/Строка/Булево), НЕ `пер` — `пер` на верхнем уровне модуля даёт
`Синтаксическая ошибка: ожидается top-level декларация`. Тесты,
которым нужно наблюдать побочный эффект ИЗ обработчика, запущенного
внутри `запусти`-спавненного серверного процесса (например "обработчик
вызван N раз"), не могут использовать общий mutable-счётчик — даже
если бы top-level `пер` был разрешён, `отправить()`/межпроцессный
обмен в этой VM копирует данные по значению между процессами, а не
делит память. `test_приложение.pns` вместо счётчика проверяет
поведение КОСВЕННО — по форме и статусу ответа (структура ошибки vs
`Задача.в_json()` — обработчик логически не мог быть вызван, если тело
ответа не похоже на его результат).

## Вопрос 5 — откуда OpenAPI-генератор берёт список маршрутов?

`http.Маршрутизатор.маршруты: Массив(Маршрут)` — ПОЛЕ, не приватное на
уровне языка (в panos нет `приватный`/`публичный` полей структуры,
только на уровне модуля через `экспорт`). Однако `тип Маршрут`
(`http.pns` строка ~475) объявлен БЕЗ `экспорт` — значит недоступен
по имени из другого модуля (`быстряга`) для деструктуризации напрямую
(`выбор`/pattern на неэкспортированный тип из чужого модуля скорее
всего не типизируется — нужно перепроверить в plan/tasks). Раз
`быстряга.Приложение` оборачивает СВОЙ собственный `http.
Маршрутизатор`, но параллельно ведёт СВОЙ список зарегистрированных
типизированных маршрутов (с метаданными — путь, метод, есть ли
`ОписаниеСхемы`) — OpenAPI-генератор читает метаданные `быстряга`, не
лезет в приватные поля `http.Маршрут`. Это ЕСТЕСТВЕННО следует из
Вопроса 1 (генерация обёрток регистрации уже требует, чтобы `быстряга`
сама вела список — заодно там же хранятся путь/метод/схема для
`/openapi.json`), отдельного велосипеда не нужно.

## Вывод

Архитектурно `быстряга` — это ГЕНЕРАТОР ОБЁРТОК поверх
`http.Маршрутизатор` + собственный список метаданных маршрутов для
`/openapi.json` + middleware-цепочка (композиция функций перед вызовом
финального `ОбработчикМаршрута`, тоже без нового транспортного
механизма). Ничего из этого не требует изменений в `panos/core` или
`std/сеть/http.pns`.
