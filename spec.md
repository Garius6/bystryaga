# Спецификация: быстряга — типизированный HTTP-фреймворк для panos

**Пакет**: `panosiki/быстряга` (новый git-репозиторий, `pan`-управляемый)
**Создано**: 2026-08-20
**Статус**: Draft
**Вход**: "Следующая задача — создание fastapi-like фреймворка на panos"

## Контекст

В `panos/std/сеть/http.pns` уже есть рабочий HTTP-слой: `обслуживать`/
`обслуживать_слушатель` (сервер поверх native `сеть.http_сервер_слушать`),
`Маршрутизатор` (регистрация маршрутов по методу+шаблону пути с `:param`,
`.как_обработчик()`), `статический_обработчик` (раздача файлов). Всё это —
СТРОКОВЫЙ уровень: обработчик получает `ЗапросМаршрута` (сырое тело,
`Соответствие(Строка, Строка)` для path-параметров), сам парсит JSON через
`std/кодирование/json.pns` (`json.разобрать`/`json.разобрать_в[T: ИзJSON]`),
сам решает, что вернуть, сам собирает `ОтветСервера`.

`быстряга` — это НАДСТРОЙКА над `http.Маршрутизатор` (не замена и не
параллельная реализация роутинга/сервера), задача которой: убрать
ручной разбор/валидацию/сериализацию из каждого обработчика,
дать декларативную регистрацию маршрутов с типизированным телом
запроса/ответа, и получить бесплатную OpenAPI-документацию из уже
объявленных типов — тот же сдвиг, что дал FastAPI поверх Starlette
(Starlette = `http.Маршрутизатор` в этой аналогии).

panos НЕ поддерживает декораторы и произвольную runtime-рефлексию
сигнатур функций — поэтому синтаксис `@app.get("/x")` дословно
недостижим. Механизм в этой спеке: явная регистрация через
generic-функции (`быстряга.получить[Тело, Ответ](путь, обработчик)`),
где `Тело`/`Ответ` — обычные структуры, реализующие `json.ИзJSON`/
`json.ВJSON` (как сегодня, вручную или через `../panosiki/codegen`'s
`&Json`-аннотацию — этот механизм уже существует и не меняется).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Типизированный обработчик с авто-валидацией (Priority: P1)

Разработчик регистрирует маршрут, объявив структуры тела запроса и
ответа. `быстряга` сам: разбирает JSON-тело в структуру (или отвечает
`400` с понятным сообщением при синтаксической ошибке JSON), вызывает
валидацию структуры (если она реализует интерфейс `Валидируемое`) и
отвечает `422` с сообщением при её неудаче, вызывает обработчик уже с
готовой типизированной структурой, сериализует возвращённое значение
обратно в JSON с `Content-Type: application/json`.

**Почему первый приоритет**: это и есть основная FastAPI-механика
("typed in, typed out, validation бесплатно") — без неё пакет не
отличается от прямого использования `http.Маршрутизатор` +
`json.разобрать_в` в каждом обработчике.

**Independent Test**: `POST /задачи` с JSON-телом `{"текст": ""}` на
структуру с валидацией "текст не пуст" — ответ `422` с сообщением
поля, обработчик НЕ вызывается. То же тело с непустым `текст` — `200`,
обработчик получает уже распарсенную, провалидированную структуру.

**Acceptance Scenarios**:

1. **Given** маршрут зарегистрирован с типом тела `Т`, **When** приходит
   валидный JSON, соответствующий полям `Т`, **Then** обработчик
   вызывается с заполненной структурой `Т`, без ручного парсинга в
   теле обработчика.
2. **Given** тот же маршрут, **When** тело — синтаксически некорректный
   JSON, **Then** ответ `400` с телом-ошибкой (структурированной, не
   голым текстом), обработчик не вызывается.
3. **Given** `Т` реализует `Валидируемое`, **When** JSON распарсился, но
   `.проверить()` вернула ошибку, **Then** ответ `422` с сообщением из
   `.проверить()`, обработчик не вызывается.
4. **Given** обработчик возвращает структуру `О`, реализующую
   `json.ВJSON`, **Then** ответ сериализуется в JSON автоматически,
   `Content-Type` выставляется без участия обработчика.
5. **Given** маршрут БЕЗ тела (`GET`, только path/query-параметры),
   **When** используется generic-регистрация с типом тела `Пусто`,
   **Then** шаг разбора JSON пропускается целиком (не пытается
   распарсить пустое тело как JSON).

### User Story 2 — Автогенерация OpenAPI/Swagger документации (Priority: P2)

`быстряга.документация(апи)` возвращает `Обработчик`, который отдаёт
`GET /openapi.json` (валидный OpenAPI 3.x документ, собранный из
РЕАЛЬНО зарегистрированных маршрутов — метод, путь, path-параметры) и
`GET /docs` (минимальная HTML-страница, тянущая готовый Swagger UI
с CDN, указывающая на `/openapi.json` — не пишем свой UI с нуля).

**Почему второй приоритет**: не блокирует базовое использование
фреймворка (US1 работает и без документации), но именно ради этого
куска обычно и выбирают FastAPI-style фреймворк вместо голого роутера.

**Independent Test**: реальный HTTP-запрос `GET /openapi.json` на
приложение с 2 зарегистрированными маршрутами (`GET /задачи`,
`POST /задачи` с типизированным телом) — ответ парсится как валидный
JSON, содержит оба пути с правильными методами.

**Acceptance Scenarios**:

1. **Given** маршрут зарегистрирован с типом тела `Т`, реализующим
   новый интерфейс `ОписаниеСхемы` (см. FR-010), **Then**
   `/openapi.json` содержит JSON Schema тела запроса с именами и
   типами полей `Т`.
2. **Given** маршрут зарегистрирован БЕЗ `ОписаниеСхемы` на типе тела
   (интерфейс не реализован), **Then** `/openapi.json` всё равно
   содержит путь/метод/summary — просто без детальной схемы тела
   (`{}` вместо развёрнутого JSON Schema). Деградация, не падение.
3. **Given** приложение с `N` маршрутами, **When** `GET /docs`,
   **Then** ответ — валидный HTML, ссылающийся на `/openapi.json` и
   CDN-скрипт Swagger UI, без бандлинга JS в репозиторий.

### User Story 3 — Middleware и хуки жизненного цикла (Priority: P2)

`Приложение` (обёртка над `http.Маршрутизатор`) поддерживает
регистрацию middleware-функций (`функ(ЗапросМаршрута, Далее) ->
ОтветСервера`, где `Далее` — продолжение цепочки) и хуков
`при_старте`/`при_остановке` (вызываются вокруг `http.обслуживать`).

**Почему третий приоритет**: логирование запросов, CORS, auth-заголовки
— частые, но не блокирующие MVP-фреймворка потребности; без них US1/US2
уже дают самостоятельную ценность.

**Independent Test**: middleware, логирующий метод+путь каждого
запроса в массив (тестовый sink вместо stdout) — после `N` запросов
через `Приложение` массив содержит ровно `N` записей в правильном
порядке, включая случаи когда сам обработчик вернул ошибку.

**Acceptance Scenarios**:

1. **Given** зарегистрировано 2 middleware `M1`, `M2` (в этом
   порядке) и обработчик `H`, **When** приходит запрос, **Then**
   порядок вызова — `M1` → `M2` → `H` → (ответ `H` проходит обратно
   через `M2`/`M1`, если они решают его модифицировать).
2. **Given** зарегистрирован `при_старте`-хук, **When** `Приложение.
   запустить(порт)` вызван, **Then** хук выполняется РОВНО ОДИН РАЗ
   до первого принятого запроса.
3. **Given** middleware сам возвращает ответ, не вызывая `Далее`,
   **Then** обработчик маршрута и последующие middleware не
   вызываются (короткое замыкание — так реализуется, например, auth).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `быстряга.Приложение` MUST оборачивать `http.
  Маршрутизатор` — вся логика сопоставления путей/методов (включая
  `:param`-извлечение) переиспользуется как есть, не дублируется.
- **FR-002**: Регистрация типизированного маршрута (`получить[Ответ]`,
  `отправить_пост[Тело, Ответ]`, `отправить_put[Тело, Ответ]`,
  `отправить_patch[Тело, Ответ]`, `удалить[Ответ]` — симметрично
  существующим методам `Маршрутизатор`) MUST принимать фабрику
  нулевого значения `Тело` (`функ() -> Тело`) отдельным аргументом —
  panos не умеет сконструировать generic-параметр "из ничего" внутри
  чужого кода (см. `research.md` Вопрос 1), поэтому вызывающий обязан
  передать способ получить пустой инстанс явно, а не полагаться на
  скрытый конструктор по умолчанию. MUST требовать, чтобы `Тело`
  реализовывал `json.ИзJSON + Валидируемое` (кроме `Пусто` — см.
  FR-005) и `Ответ` реализовывал `json.ВJSON`. (Пересмотрено при
  research: `Валидируемое` — ОБЯЗАТЕЛЬНЫЙ bound, а не опциональный —
  panos не умеет условно проверять "реализует ли generic-параметр
  интерфейс" в рантайме; см. `research.md` Вопрос 3/4. Структуре без
  реальной валидации ничего не стоит реализовать `.проверить()`
  тривиально, возвращая `Опция.Нет()` всегда.)
- **FR-003**: При синтаксической ошибке JSON в теле запроса система
  MUST вернуть `400` со структурированным телом-ошибкой (`{"ошибка":
  "..."}"), не дойдя до пользовательского обработчика.
- **FR-004**: Система MUST вызвать `Тело.проверить()` (`Валидируемое`
  — `функ проверить(это: Тело) -> Опция(Строка)`) сразу после
  успешного разбора JSON и до вызова обработчика; `Опция.Есть(
  сообщение)` MUST давать ответ `422` с этим сообщением, обработчик
  не вызывается.
- **FR-005**: Тип тела `Пусто` (для маршрутов без тела — `GET`/
  `DELETE`) MUST полностью пропускать шаг разбора JSON, не требовать
  реализации `ИзJSON` от `Пусто`.
- **FR-006**: Возврат обработчика (`Ответ`, реализующий `ВJSON`) MUST
  сериализоваться автоматически через `json.сериализовать_из`,
  `Content-Type: application/json` MUST выставляться без участия
  обработчика.
- **FR-007** (пересмотрено при реализации T012-T016): обработчик MUST
  ВСЕГДА возвращать `быстряга.Отклик(О) = структура { статус: Число,
  тело: О }`, не голый `О` — panos статически типизирован, у функции
  ровно ОДИН тип возврата, "либо О, либо Отклик(О)" не выразимо без
  двух отдельных сигнатур обработчика на каждый HTTP-метод (что удваивает
  API-поверхность на весь фреймворк без реальной пользы). `быстряга.
  ок[О](тело: О) -> Отклик(О)` — сокращение для статуса `200`
  (самый частый случай), `быстряга.Отклик(статус, тело)` — явный
  произвольный код.
- **FR-008**: `быстряга.документация(апи)` MUST возвращать `Обработчик`,
  отдающий валидный OpenAPI 3.x JSON на `/openapi.json`, собранный из
  фактически зарегистрированных в `Приложение` маршрутов (путь, метод,
  path-параметры извлекаются из уже существующего `Шаблон_Пути`/
  `Сегмент_Шаблона` в `http.pns` — не парсятся заново).
- **FR-009**: `/docs` MUST отдавать HTML-страницу с Swagger UI через
  CDN (без вендоринга JS-бандла в репозиторий `быстряга`), указывающую
  на `/openapi.json`.
- **FR-010**: Новый интерфейс `ОписаниеСхемы` (`функ поля_схемы(это: Т)
  -> Массив(ПолеСхемы)`, где `ПолеСхемы = структура {имя: Строка, тип:
  Строка, обязательно: Булево}`) MUST быть ОПЦИОНАЛЬНЫМ — маршрут с
  типом тела/ответа, не реализующим этот интерфейс, MUST по-прежнему
  появляться в `/openapi.json` (путь+метод), просто без детальной
  JSON Schema тела.
- **FR-011**: `Приложение.middleware(ф)` MUST регистрировать функцию
  вида `функ(ЗапросМаршрута, Далее) -> ОтветСервера`, где `Далее =
  функ(ЗапросМаршрута) -> ОтветСервера`; цепочка MUST вызываться в
  порядке регистрации, с возможностью короткого замыкания (не
  вызывать `Далее`).
- **FR-012**: `Приложение.при_старте(ф)`/`.при_остановке(ф)` (`ф: функ()
  -> Пусто`) MUST вызываться `при_старте` ровно один раз перед первым
  принятым соединением, `при_остановке` — при штатном завершении
  `Приложение.запустить` (если оно вообще возвращается — `http.
  обслуживать` сегодня блокирующий, см. Assumptions).
- **FR-013**: Программы, НЕ использующие `быстряга` (обычный `http.
  Маршрутизатор` напрямую), MUST продолжать работать без изменений —
  `быстряга` не патчит и не меняет поведение `std/сеть/http.pns`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Реальный e2e-тест (настоящий сокет, не in-memory
  вызов) — `POST` с валидным JSON-телом на типизированный маршрут
  доходит до обработчика с корректно заполненной структурой, ответ —
  корректный JSON с `Content-Type: application/json`.
- **SC-002**: Тот же маршрут с невалидным JSON — `400`, обработчик не
  вызван (проверяется через side-effect счётчик вызовов).
- **SC-003**: Маршрут с `Валидируемое`-телом и невалидными данными —
  `422` с сообщением, обработчик не вызван.
- **SC-004**: `GET /openapi.json` на приложении с ≥2 маршрутами —
  ответ парсится `json.разобрать` без ошибки, содержит оба пути.
- **SC-005**: Middleware-цепочка из 2 звеньев + обработчик — порядок
  вызова подтверждён тестом (см. US3 Independent Test).
- **SC-006**: `zig build test`/`conformance` (в `panos`) не задеты —
  `быстряга` живёт целиком в `panosiki`, не трогает `panos/core`.

## Assumptions

- `http.обслуживать`/`обслуживать_слушатель` сегодня БЛОКИРУЮЩИЕ (весь
  вызов не возвращается, пока сервер не остановлен) — `при_остановке`
  из FR-012 реалистично сработает только при будущем добавлении
  штатного graceful-shutdown в `http.pns`; пока это НЕ в скоупе —
  `при_остановке` регистрируется, но может никогда не быть вызван на
  практике, это документированное ограничение, не баг `быстряга`.
- Dependency Injection (FastAPI's `Depends()`) — явно ИСКЛЮЧЕНО из
  первой версии (см. clarifying-вопрос сессии) — не проектируется и не
  упоминается дальше в этой спеке.
- Path/query-параметры остаются `Строка` на уровне `http.
  Маршрутизатор`, как сегодня — типизированное автоприведение
  (`Целое`/`Число` из path-параметра с автоматическим `422` при
  нечисловом значении) — реалистичный кандидат для follow-up спеки,
  НЕ в этой версии (только тело запроса/ответа типизированы здесь).
- `ОписаниеСхемы` пишется вручную на структурах-телах запросов —
  автогенерация через `../panosiki/codegen` (по аналогии с `&Json`) —
  естественное расширение, но отдельная задача, не блокирует US2 (см.
  FR-010 — деградация до "путь есть, схемы нет" явно допустима).
- Название пакета "быстряга" — выбор пользователя сессии; `pan.toml`
  `имя = "быстряга"`, экспортируемый модуль — `быстряга` (одно слово,
  без суффиксов).
